# CHAPTER 3: FRAMEWORK AND METHODOLOGY

## 3.1 CONCEPTUAL FRAMEWORK (Final Integrated Version)

This chapter outlines the conceptual framework and methodology for the development of **StegoLock**, a cloud based web application built on a reconstruction dependent security architecture for digital document storage. The core of this research is the **Reconstruction-Dependent Security Architecture**. This framework changes the traditional approach to security by moving beyond simply blocking access to a system. Instead, it ensures that data remains private because the information cannot be identified or put back together without the correct digital credentials. 

This model ensures that an attacker cannot find or rebuild the original data unless they have simultaneous access to the encryption keys, the map of the hidden pieces, and the encrypted data fragments stored in the cloud. This chapter also explains the design and logic of the system using the **Input-Process-Output (IPO)** method. This approach shows how sensitive user information is changed into a highly secure and invisible state. These principles guided the researchers in creating an application that follows modern security standards.

## 3.1.1 THE RECONSTRUCTION-DEPENDENT SECURITY ARCHITECTURE
The fundamental principle of StegoLock is **security through segmentation and obfuscation**. Rather than storing a document as a single file, the system breaks the data into small fragments and hides them inside everyday media (images, audio, and text). These "stego files" are subsequently stored in a centralized cloud bucket.

As illustrated in Figure 1, to reconstruct the original document, the system relies on three "pillars" that must be accessed simultaneously:
1.  **The Master Key:** This is a digital key derived from the user’s password. It serves as the unique credential required to unlock the document’s internal encryption key once the scattered data fragments have been reassembled.
2.  **The Stego Map:** This serves as a digital blueprint stored within the system’s database. It maintains a precise record of which hidden data fragments belong to a specific document and the exact order required for reassembly.
3.  **The Stego Files:** These are the physical cover media (such as images, audio, or text files) stored in the cloud. To an unauthorized party, these appear as ordinary media files, yet they secretly contain the encrypted data fragments.

**System Security:** These three pillars are functionally interdependent. If an unauthorized party accesses the files without the map, the correct data cannot be identified. If the map is accessed without the master key, the data remains encrypted and unreadable. Successful reconstruction through the **Reconstruction Module** requires the simultaneous presence of all three elements.

### Step 1: Definition of Perspective (Mental Alignment)
Before drafting, we establish a strict boundary for each section:

A. **IPO (3.1.2)**: The "Black Box" view. What goes in, what happens generally, what comes out. Given the bidirectional nature of StegoLock, the IPO model is divided into two distinct lifecycles: **Locking** and **Unlocking**.

#### 1. The Locking IPO (Protection Lifecycle)

##### Input Stage
The input stage is categorized into what the user provides and what the system provides to facilitate the security model.
- **User-Provided Inputs:**
    - **Original Document:** The sensitive document file (pdf, doc/docx, txt) to be secured.
    - **Login Credentials:** The user's email and password
- **System-Provided Inputs:**
    - **Cover Media Pool:** A curated library of pre-validated cover files (PNG images, WAV audio, and UTF-8 text) categorized by steganographic capacity. The system enforces a **Diversity Protocol**, requiring the selection of at least one cover from each media type for every document to maximize the obfuscation footprint.
    - **Cryptographic Metadata:** Salts, Nonces, and Initialization Vectors (IVs) generated by the system for each encryption session.

**Description:**
The Input Stage serves as the data-gathering and preparatory phase for the StegoLock framework. During this phase, the user supplies their primary payload (the document they want to secure) alongside their login credentials, which act as the anchor for the system's security keys. Concurrently, the system autonomously prepares the necessary operational materials by generating unique cryptographic metadata to ensure encryption uniqueness, and by selecting a diverse, capacity-matched set of cover media. At this stage, no data transformation has occurred, rather, all required user and system inputs are positioned, validated, and ready to be fed into the processing stage.

##### Process Stage
This represents the "Black Box" where the transformation happens. It is divided into three functional phases:
- **Phase A: Cryptographic Transformation**
    - **Master Key Derivation:** Converting the user password into the user's master key during a successful login session.
    - **Compression:** Reducing the payload size using Gzip to minimize the steganographic footprint.
    - **Document Encryption:** Generating a unique Document Encryption Key (DEK) wrapped by the Master Key, then using AES-256-GCM to convert the compressed payload into a secure ciphertext.
- **Phase B: Steganographic Obfuscation**
    - **Segmentation:** Breaking the encrypted ciphertext into multiple variable-sized fragments based on the capacity of the selected covers.
    - **Steganographic Embedding:** Executing Python-based multi-format steganography to securely embed fragments inside the selected cover media (images, audio, and text).
- **Phase C: Distribution & Mapping**
    - **Cloud Storage:** Uploading the generated "Stego Files" to Backblaze B2 cloud storage.
    - **Map Construction:** Finalizing the relational "Stego Map" in the MySQL database concurrently with cloud uploads (the digital blueprint for reassembly).

**Description:**
The Process Stage executes the core transformations of the Reconstruction-Dependent Security Architecture. It begins by securing the payload cryptographically, utilizing a document-specific encryption key that is safely wrapped by the session's Master Key. The resulting ciphertext undergoes physical segmentation before being concealed within diverse cover media via multi-format steganographic embedding. Ultimately, the system isolates the reassembly logic from the payload by scattering the resulting stego files into cloud storage while constructing the authoritative Stego Map blueprint in the local database.

##### Output Stage
The final state of the system after a document has been successfully processed.
- **Pillar 3: Stego Files (The Hidden Fragments):** Ordinary-looking media files scattered in the cloud that contain the encrypted data.
- **Pillar 2: Stego Map (The Digital Blueprint):** A metadata record in the database that links fragments to their respective cover files and reassembly order.
- **System Feedback:** 
    - **Secure State:** The document status is updated to Locked or Stored.
    - **Audit Trail:** Generation of activity logs for the locking lifecycle.

#### 2. The Unlocking IPO (Reconstruction Lifecycle)

##### Input Stage
The input stage for unlocking requires the correct credentials and the system's structural blueprints.
- **User-Provided Inputs:**
    - **Unlock Request:** The document identifier selected by the user.
    - **Session Master Key:** The active master key residing in the session (proving successful authentication).
- **System-Provided Inputs:**
    - **Stego Map (Pillar 2):** The database blueprint containing the required fragment IDs, cover cloud IDs, and exact offsets.
    - **Stego Files (Pillar 3):** The physical steganographic media files downloaded from the Backblaze B2 cloud.

##### Process Stage
This represents the reverse transformation where the system reassembles and decrypts the data:
- **Phase A: Retrieval & Extraction**
    - **Parallel Fetching:** Downloading the scattered Stego Files from the cloud bucket concurrently.
    - **Batch Extraction:** Executing Python-based extraction to securely retrieve the hidden encrypted fragments from the covers.
- **Phase B: Streaming Reassembly**
    - **Sequential Assembly:** Merging the extracted binary fragments back into a single ciphertext container based on the Stego Map index.
- **Phase C: Cryptographic Reversal**
    - **Key Unwrapping:** Using the session's Master Key to unwrap and recover the Document Encryption Key (DEK).
    - **Decryption & Decompression:** Reversing the AES-256-GCM encryption and Gzip compression to restore the original payload.
    - **Integrity Validation:** Verifying the restored file's hash against the original database hash to ensure no tampering occurred.

##### Output Stage
The final state of the system after a document has been successfully reconstructed.
- **The Original Document:** The bit-perfect, plaintext restoration of the user's original file, delivered securely for download.
- **System Feedback:** 
    - **Restored State:** The document status is updated to Retrieved or Decrypted.
    - **Audit Trail:** Generation of activity logs for the successful unlocking event.

B. **System Architecture (3.1.2.1)**: The "Blueprint" view. Where components sit and how they are connected.

#### 3.1.2.1 System Architecture
The StegoLock system utilizes a **Four-Tiered Layered Architecture** to separate user interaction, application logic, local metadata persistence, and remote cloud storage. This separation of concerns is vital for enforcing the Reconstruction-Dependent Security Model, ensuring that the components housing the Stego Map (the blueprint) and the Stego Files (the encrypted payload) are physically and logically isolated from each other.

##### Layer 1: Presentation Layer (User Interface)
The client-facing tier is built using **React** and driven by **Inertia.js**. This layer serves as the user's portal to interact with the system without needing to understand the underlying cryptographic complexity. 
- **Functionality:** It captures the initial user inputs (Original Document and Login Credentials), visualizes the status of the documents, and provides real-time feedback during the locking and unlocking lifecycles.
- **Security Boundary:** No raw cryptographic processing or data segmentation happens in the client's browser. All sensitive operations are delegated securely to the backend to prevent client-side tampering.

##### Layer 2: Application Logic Layer (System Controller)
This is the core operational tier, acting as the system's central nervous system. It is composed of a dual-stack environment:
- **Laravel (PHP) Subsystem:** Acts as the primary controller. It handles HTTP routing, session authentication, user access controls, and acts as the secure bridge to the database and cloud storage.
- **Python Stego-Engine Subsystem:** Invoked dynamically by Laravel, this specialized subsystem is solely responsible for executing the multi-format steganographic embedding and extraction processes.

##### Layer 3: Persistence Layer (Local Database)
Powered by **MySQL**, this layer is dedicated to structural metadata and identity management.
- **Role in the Security Model:** This layer strictly houses **Pillar 2: The Stego Map**. It stores the relational database tables that record fragment IDs, the target cover files, reassembly indices, and document integrity hashes.
- **Isolation Constraint:** To maintain the reconstruction-dependent paradigm, this layer **never** stores the user's plaintext password, the derived document encryption keys, or the actual document ciphertext. 

##### Layer 4: Storage Layer (Cloud Infrastructure)
Powered by **Backblaze B2 Cloud Storage**, this external tier is dedicated to scalable, secure file hosting.
- **Role in the Security Model:** This layer strictly houses **Pillar 3: The Stego Files**. It acts as the remote repository for the ordinary-looking media files (images, audio, text) that secretly contain the encrypted document fragments.
- **Isolation Constraint:** The cloud bucket possesses no knowledge of the Stego Map or what fragments belong to which user. It merely stores flat binary objects.

##### The Communication Path (The Secure Bridge)
A critical security feature of StegoLock's architecture is its strict communication pathway. **Layer 3 (Database)** and **Layer 4 (Cloud Storage)** are completely siloed and never communicate with each other directly. 
- **Layer 2 (Laravel)** acts as the sole, authoritative bridge. 
- During the reconstruction lifecycle, the Application Logic Layer must query the Persistence Layer for the Stego Map. Using that map, it authenticates with the Storage Layer via a secure API to retrieve the specific Stego Files. 
- This architectural chokepoint ensures that a compromise of the database yields useless blueprints without the cloud files, while a breach of the cloud storage yields encrypted noise without the database blueprints.

**Summary of Functional Features**
To sum it all up, the following list highlights how the complex background processes discussed previously power the actual features users interact with inside the StegoLock application:

*   **User Registration:** Securely creating an account and generating the user's unique digital keys behind the scenes.
*   **User Authentication:** Verifying the user's identity at login so they can safely lock and unlock their files.
*   **Upload (Document Locking):** Taking a normal file, encrypting it, breaking it into pieces, and hiding those pieces in the cloud.
*   **Download (Document Unlocking):** Finding the hidden pieces in the cloud, putting them back together, and decrypting them to restore the original file.
*   **Document Sharing:** Giving a designated recipient a secure key to open a file without having to make a second heavy copy in the cloud.
*   **Document Deletion:** Using a "cloud-first" approach to completely and permanently wipe out a file's pieces from the cloud before deleting its records from the database, ensuring absolutely nothing is left behind.
